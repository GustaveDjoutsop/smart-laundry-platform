## 1. Why this document exists

An earlier hardening pass ("Phase 0") stripped hardcoded secrets out of `application.yml` and `application.yaml` and replaced them with empty env placeholders such as `${CAMPAY_APP_SECRET:}`. That work was done correctly and is verifiable at HEAD.

It was, however, **incomplete in two ways**:

1. **It missed non-Spring config files.** A live Twilio account SID and auth token remained in the root `docker-compose.yml` at HEAD until this PR. `docker-compose.yml` was never in scope of the original stripping.
2. **Stripping is not rotation.** Every value removed from a file is still recoverable from git history:
   ```bash
   git log -p --all | grep -i 'secret\|token\|key'
   ```
   This repository is private, but "private" is not a security boundary for a credential — it is recoverable by every current collaborator, every past collaborator, every machine that has ever cloned it, and any CI system with read access.

The only remediation that actually works is **rotation at the provider**. Everything else is housekeeping.

### Severity reasoning

**#1 and #2 — Twilio (do these first).** A Twilio account SID plus auth token is full API access to the account. An attacker can send SMS and WhatsApp messages billed to you, and pull message history including customer phone numbers and message bodies. This is the only credential in the list with direct, uncapped financial exposure. Worth noting: nothing in the codebase consumes `TWILIO_*` — the platform moved to the Meta WhatsApp Cloud API, and the root `backend` compose service is a dead prototype whose `Dockerfile` references a `package.json` and `prisma/` directory that no longer exist. So this credential was exposed for no operational benefit whatsoever.

**#3 — `ENCRYPTION_MASTER_KEY` (subtle and the most serious in the long run).** This is the AES key used by `EncryptedStringConverter` (`bot-core/.../persistence/converter/EncryptedStringConverter.java`) to encrypt customer PII at rest — the converter requires exactly 64 hex chars, matching the leaked value's shape. If this key is still in use in any environment, then **the encryption of customer data provides no protection against anyone holding repo history**: they have both the ciphertext design and the key. Rotating it is more involved than the others because existing ciphertext must be re-encrypted, not merely re-keyed — see §4.

**#4 — Meta token.** Committed inside a test that verifies redaction, which is a genuinely ironic place to leak a live token. Grants access to send WhatsApp messages as your business number.

**#5 — Phone number.** Not a credential, but it is personal data in a public-facing artifact of a GDPR-conscious codebase that implements Art. 17 erasure (see `ADR-008`). Inconsistent to purge customer numbers from the database while shipping one in a test fixture.

## 3. What this PR changes

Code changes only. **No rotation has happened yet** — rotation requires provider dashboard access and is tracked in §4.

- `docker-compose.yml` — Twilio SID/token/number/webhook replaced with `${VAR:-}` env indirection.
- `BotManagerService/test/redact.test.js` — real Meta token and real phone number replaced with obvious fakes (`EAAFAKEfake000TEST…`, `+491700000000`). The test asserts the same behaviour; only the fixture changed.
- `.gitleaks.toml` — new. Extends the default ruleset with six project-specific rules (CamPay, Meta, EQLink, mobile money, Twilio auth token, 64-hex master key). Allowlist is narrow and every entry states its reason.
- `.github/workflows/secret-scan.yml` — new. **Blocking** gitleaks gate: working-tree scan on every PR, push and weekly; plus a PR-range scan of only the commits a PR adds.
- `scripts/audit-git-history-secrets.sh` — new. Reproducible history inventory; this is what generated §2.

### Verification performed before merge

The config was validated rather than assumed, because a secret-scanning gate that misfires gets switched off:

1. **First draft reported 28 findings, all false positives.** The custom rules matched the variable *name* (`APP_SECRET`) instead of its value, because gitleaks reports the first capture group as the secret. Fixed by adding `secretGroup = 1` to every rule so the value is captured, then narrowing the remaining noise with justified allowlist entries. Working tree now scans **clean**.
2. **Negative test.** A canary file containing a real-format Twilio token, CamPay secret, 64-hex master key and Meta `EAA…` token was scanned: **all four custom rules fired**, plus the upstream Facebook rule. The gate detects what it claims to.
3. Env indirection (`${CAMPAY_APP_SECRET:}`) produces no findings, confirming correctly parameterised config is never flagged.

### A note on scan scope

A full-history scan reports 47 findings and always will, because the historical leaks are remediated by rotation (§4), not by rewriting history (§5). A permanently red job trains people to ignore it, so the workflow scans only things that can be green and stay green: the current working tree, and the commits each PR adds. Historical review is done on demand with `scripts/audit-git-history-secrets.sh`.

## 4. Rotation checklist — provider actions

These cannot be done from CI or from the repo. Work top to bottom; the order is by blast radius.

### 4.1 Twilio — do first

- [ ] Log in to the [Twilio Console](https://console.twilio.com/)
- [ ] Check **Monitor → Logs → Messaging** for any message you did not send. If there is unexpected traffic, this is an incident, not just a rotation: capture the log and check billing before proceeding.
- [ ] **Account → API keys & tokens → Auth Token → Rotate** (Twilio calls this "secondary token" promotion)
- [ ] Since nothing consumes `TWILIO_*`, prefer the stronger option: **close the Twilio subaccount entirely** if it is no longer needed. A closed account cannot be abused.
- [ ] If keeping it, store the new token in Doppler only. Do not add it to any `.env` file.

### 4.2 `ENCRYPTION_MASTER_KEY` — needs a data migration, not just a new value

Rotating this one carelessly makes existing encrypted rows permanently unreadable. Sequence:

- [ ] Determine whether the leaked key is actually in use: compare it against the current `ENCRYPTION_MASTER_KEY` in Doppler (`spring-bot-manager` → each config).
- [ ] **If it is NOT in use** — it was a local dev key only — tick this section off and record that below. No migration needed.
- [ ] **If it IS in use**, do a proper re-key:
  1. Take a fresh verified backup first (see [`docs/DISASTER-RECOVERY.md`](./DISASTER-RECOVERY.md) once R3 lands — do not skip this).
  2. Generate a new key: `openssl rand -hex 32`
  3. Write a one-off migration task that reads each encrypted column with the OLD key and writes it back with the NEW key, inside a transaction, for every entity using `@Convert(converter = EncryptedStringConverter.class)`.
  4. Run against a restored copy of production first and verify decryption of a known row.
  5. Swap the Doppler value, deploy, and confirm reads work before deleting the old key from your records.
- [ ] Consider adding a key-version column so future rotations do not need a full re-encrypt.

### 4.3 Meta / WhatsApp Cloud API

- [ ] [Meta for Developers](https://developers.facebook.com/) → your app → **WhatsApp → API Setup**
- [ ] Revoke the exposed token; generate a new **System User** token (permanent tokens are preferable to 24h tokens for a production webhook consumer)
- [ ] Rotate the **App Secret** as well (App Settings → Basic) — webhook signature verification depends on it, and `WHATSAPP_VERIFY_SIGNATURE: "true"` in prod means a wrong value fails closed, which is the safe direction
- [ ] Update Doppler: `WHATSAPP_ACCESS_TOKEN_*`, `WHATSAPP_APP_SECRET*`, `META_VERIFY_TOKEN_*`
- [ ] Send one test message through each bot to confirm

### 4.4 Precautionary rotations

Not proven exposed, but they appear as env keys throughout history and are cheap to rotate while you are in each dashboard:

- [ ] **CamPay** — app key, app secret, webhook secret. Payment credentials; rotate on principle.
- [ ] **Auth0** — M2M client secret for each application. Note the `sls-*` scope set must be preserved on the new credential.
- [ ] **Database passwords** — `smartbot`, `machinedb`, `paymentdb` (Supabase → Settings → Database).
- [ ] **Grafana Cloud** — `remote_write` API key.
- [ ] **MQTT broker** password, if the Mosquitto instance is network-reachable.

## 5. Why we are not rewriting git history

`git filter-repo` / BFG can scrub these values from history. We are deliberately **not** doing that:

- Once rotated, the leaked values are **inert**. Scrubbing removes a record of something that no longer works.
- A history rewrite changes every commit SHA across a repo with 90+ merged PRs. Every clone breaks, every PR reference and code-review link rots, and CI caches keyed on SHA invalidate.
- Clones already taken are unaffected by a rewrite anyway — anyone who cloned before still holds the old objects. Rewriting creates a false sense of remediation.

Rotation is the fix. Scrubbing is cosmetic. If a compliance requirement later demands scrubbing, do it as a planned, announced operation — not as part of incident response.

## 7. Preventing recurrence

| Control | Mechanism | Status |
|---|---|---|
| Block secrets entering new PRs | `.github/workflows/secret-scan.yml` (gitleaks, blocking) | This PR |
| Catch anything the PR scan missed | Weekly full-history gitleaks sweep | This PR |
| Detect what is already in history | `scripts/audit-git-history-secrets.sh` | This PR |
| Central secret storage | Doppler, per-service projects with `dev`/`ci`/`prd` | Already in place |
| Keep secrets out of local files | `.gitignore` covers `.env`; use `doppler run --` instead | Already in place |

**One habit worth adopting:** run `doppler run -- <command>` locally instead of exporting variables into a shell or writing `.env` files. The Twilio token leaked because a working local config was committed as a convenience. Nothing that never lands in a file can be committed by accident.
